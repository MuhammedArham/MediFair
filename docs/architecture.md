# Architecture

## Current base application

MediFair AI is a Next.js App Router application with TypeScript and Tailwind CSS. The current build has fictional-only case onboarding, patient-reviewed quote-request drafts, a mock-first email transport, a local reply simulator, and an explicit Resend send/receive adapter. There is no live patient intake. Matched replies and private PDFs use the shared structured extraction pipelines. Navigation covers `/`, `/case/new`, `/case/[id]`, `/providers`, `/requests`, `/inbox`, `/comparison`, and `/negotiation`.

Prisma 7 with `@prisma/adapter-pg` persists synthetic data in PostgreSQL through `DATABASE_URL`. The case, providers, inbox, and comparison pages read records at request time. `DEMO_MODE=true` is the safe default.

## Persistence model

`PatientProfile` records fictional identity and consent timestamps; `InsuranceProfile` records policy type, membership, known excess and coverage verification separately. A `Case` links them to a clinician-confirmed procedure, laterality, location, workflow status and an **illustrative** MBS item. Its `SourceReference` holds the genuine government item URL, retrieval and effective-date notes. Official references have no financial relationship to fictional quotes.

`Provider` has `DEMO` or `VERIFIED_EXTERNAL` source type, specialty, website, contact provenance and verification status. `CaseProviderSelection` stores a unique case/practice pair; the repository limits each case to three in a transaction and audits replacement edits. `VERIFIED_EXTERNAL` means **user-verified contact details**, not independent verification by MediFair AI. Such entries are scoped to one case. Only user-verified contacts on the server's demo allowlist can be emailed; fictional `.example` fixtures cannot. `Hospital` and `ProviderHospital` normalise known seeded associations; a manual hospital name is stored only as a user report. A versioned `QuoteRequest` stores exact recipient and text, approval identity, timestamp and content hash. `OutboundSend` stores one immutable send claim per approved request with a unique idempotency key, opaque reply address, exact payload snapshot, provider ID and status. `EmailMessage` retains accepted outbound text and the Resend ID; `EmailEvent` provides replay-safe unique delivery event IDs. `Document` stores metadata and a private storage key; PDF bytes stay outside public/.

`Quote` belongs to a case and provider, carries source links, issue/expiry dates, completeness, confirmation and revision lineage. `CostLineItem` separates billed amount, known benefit and patient responsibility by category and payer, with source locators. All financial fields are nullable integer cents; unknown is never zero. `Opportunity` records evidence and confidence. `Negotiation` links original and optional revised quotes plus outcome. `AuditEvent` records approvals and simulated workflow outcomes. PostgreSQL foreign keys and unique constraints protect relationships and email identifiers; Zod and repository checks validate writes and cross-case source links. A single-operator Basic-auth gate protects the synthetic deployed workspace; it is not patient-level authorization.

`prisma/seed.ts` creates a deterministic fictional one-eye cataract case, DemoCover, three fictional Sydney practices, three synthetic quote responses, one incomplete quote and a draft negotiation. `prisma/reset.ts` removes the deterministic demo set. Seeding sends no email. Harbour and Northside have explicitly synthetic complete fee, benefit, excess and patient-gap figures; City is missing anaesthetist and facility fees. The MBS item reference remains separate from every fictional financial amount.

## Fictional onboarding

`/case/new` uses four client-side steps: procedure, insurance, preferences and consent. The shared Zod schema validates each step and the final server action validates again. A fictional cataract autofill is available, but it never pre-checks consent. The action rejects writes when `DEMO_MODE=false`, creates a fictional patient profile, insurance profile, draft case and one-to-one `CasePreference` in one transaction, and audits consent and case creation. The insurer confirmation answer is stored as `PATIENT_REPORTED_CONFIRMED`, not an independently verified benefit. Unknown excess, co-payment and budget stay `null`.

After saving, `/providers?case=<id>&created=1` shows a confirmation summary and a selectable shortlist. The seeded fictional eye practices appear only for an ophthalmology case. A patient can select at most three or add a practice with user-verified name and email, source description, optional HTTPS source/website links and a separate verification acknowledgement. Manual contact edits and selection changes are audited; selections do not send email. Drafts with no quote requests or quotes can be edited at `/case/new?edit=<id>`; changing the procedure or specialty clears the existing selection so clinical suitability is not assumed. The form asks for no Medicare number, membership ID or detailed diagnosis. This remains a synthetic single-operator demo without patient-level authorisation and must not be used for real health information.

## Quote workflow

1. Patient creates a fictional case with the minimum information required for comparable requests. Validate with Zod and avoid storing unnecessary clinical details.
2. Patient chooses up to three practices using fictional examples or contact details they checked themselves. Provider suitability must be confirmed by a healthcare professional. Do not scrape directories or infer addresses.
3. `/requests?case=<id>` displays one editable template per selected practice. Unconfirmed MBS items and missing insurer details remain unknown. Saving, approval and rejection are separate, audited actions; editing after approval creates a new version. Approval covers the exact recipient, subject and body and does **not** send. Optional OpenAI use selects only a tone for a deterministic opening from synthetic facts.
4. A separate Send action checks explicit confirmation, current selection, consent, exact approved hash, unchanged practice address, user verification, demo allowlist, non-fixture address and a generic subject before the Resend adapter can send. `EMAIL_TRANSPORT=mock` uses the same approved payload pipeline and persists a synthetic message as `SIMULATED`; it makes no external calls. A database-unique `OutboundSend` claim and Resend idempotency key block duplicates. From and Reply-To headers contain no patient name or email. The opaque Reply-To alias is unique to case, provider and request version.
5. In Resend mode, `/api/resend/webhook` verifies the raw signed webhook with the Resend SDK. It deduplicates delivery events and processes `email.received` by retrieving full content via the Receiving API. Mock mode returns 404 before constructing a Resend client. Both modes use the same inbound persistence, reply matching, quote-response classification and quote-shell creation flow. No real send or API request was exercised during implementation; tests use mocked SDK calls.
6. Inbound emails preserve source text and create quote revisions through the shared extraction pipeline. The comparison reads the latest source-dated quote per provider, retains older versions and uses only reviewed or original structured extraction values. Unknown coverage remains unknown.

## Quote comparison

`src/lib/comparison/engine.ts` is a deterministic integer-cent calculator. It sums itemised gross provider fees and checks the stated total, then subtracts separately stated Medicare and insurer benefits exactly once and adds excess/co-payment exactly once. A stated patient gap is cross-checked, never added to. Unknown values remain `null`; missing charges, arithmetic mismatches, expired quotes, unverified cover and unconfirmed clinical scope prevent ranking. The comparison uses neither an MBS schedule fee nor a provider's unsupported benefit assumption as a patient cost.

`/comparison` shows three fictional provider cards, expandable fees, missing information, current versions and a side-by-side table. Only complete quotes for the explicitly confirmed case scope receive a lowest-cost highlight. `/comparison/quote/[id]` retains the source email, evidence, correction link, version history and audit events. The patient can record an evidence check and the clinician's scope confirmation with a note; an evidence check does not change insurer coverage status. A missing-information form creates an editable `QuoteRequest` draft and sends nothing; exact-message approval remains in `/requests`. Negotiation starts as a quote-linked unsent draft. New inbound versions are ordered by source email date so an older delayed reply cannot displace a newer one. The seeded scope confirmations and DemoCover confirmation are fictional fixtures only.

## Medical cost negotiation workflow

`/negotiation` accepts a current `ReviewOpportunity` from the deterministic opportunity engine. Eight request templates cover gap cover, specialist fee, hardship, itemisation, discrepancies, possible errors, insurer benefit review and a written revised quote. Drafts use the fictional case's original quote, evidence, insurance and preferences. Hardship and discretionary fee statements require the patient's explicit preference record. The quoted patient gap stays unknown if the source does not establish it. Official references provide cost-information context, not a legal entitlement or promised reduction.

`NegotiationRequest` versions preserve recipient, subject, original draft, approved final body, content hash, approver and timestamp, disclosure list, source document IDs, reply token, idempotency key and provider message ID. The patient can edit or reject a draft. Editing clears approval or creates a follow-up version. A separate confirmed send action claims the latest approved version exactly once. Mock transport validates that approval against the database, adds a synthetic `EmailMessage` to the normal inbox and marks it `SIMULATED`, never delivered. Real Resend sending uses the same approval record, verifies the sending domain, blocks `.example` addresses, requires the demo allowlist and a user-verified external practice or user-confirmed insurer contact. Resend SDK behaviour is exercised only with injected mocks in tests. The public synthetic demo UI requires the single-operator access gate; it is not patient account authentication.

The existing inbound matcher now accepts negotiation reply tokens, provider message references or an explicit stored thread ID; it checks the sender against the approved recipient and deduplicates by external message ID. It saves the source and attachment metadata before extraction. Negotiation and ordinary quote replies share the same `processQuoteExtraction` and `ingestInboundEmail` path. `NegotiationResponse` retains the structured interpretation, provider mode, errors and linked revised quote. In mock AI mode, only exact checked-in synthetic response fixtures are interpreted. Edited or unfamiliar replies remain visible and need manual review. The OpenAI implementation uses the configured model and Responses structured output with Zod validation; demo mode transmits only exact synthetic fixtures if deliberately enabled. There is no silent mock fallback.

The explicit state graph supports `DRAFT`, `AWAITING_APPROVAL`, `SIMULATED_SENT`, `SENT`, `AWAITING_RESPONSE`, `NEEDS_CLARIFICATION`, `COUNTEROFFERED`, `ACCEPTED`, `REJECTED` and `CLOSED`. `AuditEvent` and `EmailMessage` preserve decisions and thread history. A newly extracted revised quote is linked only if its scope, proposed MBS items, facility, fee categories and inclusions match the original and all stated amounts pass integer-cent arithmetic checks. The comparison then recalculates from the new version while retaining the original. The dashboard labels the difference a **potential quoted reduction**; an actually realised saving remains unestablished. A conditional offer, changed inclusions, unknown benefit or incomplete itemisation cannot produce a comparable reduction.

The seeded case starts with fictional Harbour at $2,400, Northside at $1,800 and City incomplete. A Northside gap-cover request can receive the exact synthetic revised quote with a $900 patient gap and unchanged quoted service scope. The simulator also includes refusal, smaller or conditional offers, more-information requests, changed inclusions and itemisation responses. Seeding itself approves or sends no negotiation message.

## Email transport and inbox workflow

`EMAIL_TRANSPORT=mock` is the default and does not create a Resend client or make network calls. The `EmailTransport` interface separates outbound send/status methods from inbound retrieval/thread methods. Both adapters feed the same approval, persistence, matching, and response-classification logic. Mock sends are saved with synthetic IDs and `SIMULATED` status; they are not marked delivered. `EMAIL_TRANSPORT=resend` opts into the real SDK adapter, requires credentials, and never falls back to mock on error.

Quote reply processing is a second interchangeable server-only pipeline. `AI_PROVIDER=mock` recognizes only deterministic fixture markers; any other text is saved as unsupported for manual review rather than guessed. `AI_PROVIDER=openai` requires a server-side `OPENAI_API_KEY` and explicit `OPENAI_MODEL`, and uses the OpenAI JavaScript SDK Responses API structured output parser with Zod validation. It never falls back to mock. In demo mode, the processing path only passes fictional case, patient, and email records. `QuoteExtraction` retains structured extraction, mode, failure state, review correction and linked `QuoteEvidence`; the original `EmailMessage` remains intact. Financial amounts are integer AUD cents or null. Deterministic checks flag inconsistent totals and do not compute unknown patient costs. Corrections update quote line items transactionally and are audited. `/quote-analysis` presents original messages beside extracted data, evidence, missing fees, review flags and a correction editor. No live AI requests are made in mock mode.

The `/dev/email-simulator` route and server action require development `NODE_ENV`, mock transport, and a loopback host. Synthetic replies use the same `ingestInboundEmail` path as Resend webhook replies. The real `/api/resend/webhook` route is disabled in mock mode, verifies the untouched body using the Resend SDK, retrieves full content through the receiving API, then matches with an opaque Reply-To token or explicit thread references. Sender mismatch and unmatched messages remain unassigned; subject matching is intentionally unsupported. The core intake stores escaped-as-text content and metadata-only attachments, marks the message untrusted, and classifies quote-response state without asserting a patient total. The inbox displays thread ID, direction, local simulation/real state, timestamps, response status, and read/unread state.

## Boundaries to implement before live use

- Authentication, authorisation, data retention/deletion, secure uploads, encryption strategy, audit history, consent records, and incident handling.
- Production rate limiting and identity controls. Exact-content approvals, recipient allowlists and replay-safe signed webhooks already exist.
- Privacy review for any real health data and external processors, including Australian Privacy Principles and cross-border disclosure obligations. Do not transmit real health records to OpenAI.
- Ongoing verification and maintenance of the existing official source registry and rule evidence.

## Dependencies and responsibilities

Next.js renders routes and hosts server-side orchestration. Prisma/PostgreSQL is runtime persistence; historical SQLite remains a test fixture. OpenAI is reserved for structured extraction, Resend for approved outbound and verified inbound mail, Zod for runtime validation, Vitest for logic tests, and Playwright for user flow checks. No undocumented external endpoint is assumed.

## Local document and bill review workflow

The `Document` table stores metadata, SHA-256, case/provider linkage, fictional source type and a private random storage key. `DocumentAnalysis` is a one-to-one record containing extracted page text, immutable initial structured interpretation, separate reviewed values, mode, status and review note. `BillReviewOpportunity` links an auditable comparison finding to source documents and optionally to a quote; an optional unique link on `Negotiation` creates one unsent draft for that finding. The document migration chain is `20261011071437_document_analysis`, `20261011071857_document_review_note`, `20261011072307_bill_negotiation_link`.

The server validates PDF extension, MIME, header, byte size and page count. `pdf-parse` reads text only; damaged files fail, and unreadable/scanned PDFs enter manual review. Random-key files use private local storage in development or private Vercel Blob in production; the download route checks workspace access and a stored digest. The Blob SDK automatically uses the connected store's `BLOB_STORE_ID` and rotating Vercel OIDC credentials; legacy read/write tokens remain supported. Missing or rejected credentials fail without changing storage mode. Deletion removes metadata and the private file while leaving an audit event. A storage path symlink into `public/` is rejected.

The document interpretation interface shares the mock/real switch pattern with email quote extraction. The mock adapter recognizes exact synthetic PDF hashes and checks page evidence; it does not infer unfamiliar content. The OpenAI adapter is dormant in mock mode, validates Zod structured output and page evidence, and in demo mode only permits exact fictional fixtures. The deterministic comparator receives structured values and performs arithmetic and scope checks separately. It never changes unknown money to zero, never subtracts a payment from a stated balance twice and does not claim a charge is unlawful. Human edits preserve the initial extraction and are audited. The dashboard and private download route support the protected synthetic deployment. Patient account control, retention and clinical data governance remain future work.

## Australian cost review opportunities

`src/lib/opportunities/engine.ts` is a pure deterministic rule engine with eight categories, stable hashed opportunity identities and a priority score based on evidence/actionability rather than predicted success. It consumes current structured quotes, private document extractions, explicit case review preferences and documented unresolved complaints; it does not call an LLM. It delegates invoice scope and arithmetic checks to the existing bill comparator. Unknown benefits and fees remain unknown. Official URL and source limitations are defined in `sources.ts` and documented in `docs/australian-billing-rules.md`; no MBS amount or future-effective download is used.

`CaseReviewPreference`, `CaseComplaint` and `ReviewOpportunity` persist explicit intent, complaint resolution, source-backed opportunity snapshots, status and editable unsent request bodies. The `20261011073215_cost_review_engine` migration adds these tables while keeping earlier quote and bill records. The `/opportunities` page and all mutations require workspace access and fictional consented cases. Generating or editing a request creates no `EmailMessage`, approval or send; any later outbound flow must use the existing exact-message approval and transport checks.


## Integrated workspace and QA (11 October 2026)

The home route is a database-backed dashboard: current case, procedure, providers contacted, replies, incomplete comparisons, active negotiations, revised quotes and comparable potential quoted reductions. Navigation is Dashboard (`/`), Find & Compare (`/providers`), My Quotes (`/comparison`), Analyse Bills (`/documents`), Opportunities (`/opportunities`), Negotiations (`/negotiation`), Inbox (`/inbox`), Settings (`/settings`). Drafts and extraction remain linked subflows at `/requests` and `/quote-analysis`.

Case IDs travel in query strings. A local HttpOnly SameSite cookie remembers the selected case for links without a case query; this is a navigation preference, not an authentication credential. Inbox, extraction and simulators scope their queries to that case. The simulator selects the latest request with an actual outgoing thread, permitting a response to an earlier sent request even when a follow-up draft exists.

Complete baseline reply fixtures now support a newly created case, not only seeded quotes. Scope and fictional insurer confirmation are reviewed separately through an explicit audited synthetic-evidence action. Onboarding's patient-reported cover answer never becomes independent cover automatically. Negotiation revisions share extraction and integer-cent comparison. Document findings create versioned NegotiationRequest records and flow through the same approval/send/receive machinery. Closing a document negotiation dismisses its finding without asserting a billing correction.

Settings reads presence-only service configuration and never returns secret values. The reset action requires local mock mode and confirmation. It clears only the canonical demo case; shared practices, hospitals and official sources are upserted and retained so unrelated cases are not deleted or disconnected. Templates are checked-in fixtures, restored by code rather than mutable database rows.

A central Next.js proxy blocks workspace access outside loopback development and rejects cross-origin mutations. `pnpm dev` binds to 127.0.0.1. This closes previously exposed demo actions but is **not** multi-user authentication; public deployments are disabled. The signed Resend webhook retains its separate gate and is disabled in mock mode. The complete application cannot be enabled for real patients merely by setting DEMO_MODE=false.

Playwright requires a separate local `medifair_e2e` PostgreSQL database, resets it, applies PostgreSQL migrations and seeds synthetic data. It forces mock adapters with blank API keys and blocks external browser requests. Tests exercise UI actions rather than bypassing approval via database writes. Vitest separately exercises real adapter construction/error paths with injected SDK mocks. See `docs/test-results.md` for actual results and `docs/known-limitations.md` for the remaining production boundary.

## Vercel compatibility (2026-10-12)

The production Prisma schema and baseline migration are PostgreSQL; archived SQLite migrations and a test-only SQLite client retain deterministic repository tests. Runtime uses `DATABASE_URL`, while Prisma CLI may use optional `DIRECT_URL` for migrations. Prisma Client is generated during install and build; run `pnpm db:deploy` against the target database before serving traffic. The webhook and private document route use the Node.js runtime. The signed Resend webhook is exempt from the workspace Basic gate, but verifies the raw body and is disabled in mock mode. All other workspace routes and server actions use the server-side access gate. Developer simulator and reset actions stay restricted to loopback development. Documents use local private storage in development and private Vercel Blob in production; uploads are limited to 4 MB to fit the Vercel function body limit. No real patient data is supported.

## Controlled Resend account testing

Real delivery provenance (`EmailMessage.isSimulation=false`) is separate from the synthetic case classification (`Case`/`PatientProfile`/`Quote.isFictional`). Shared inbound and negotiation processing requires a consenting fictional case; extraction and correction retain synthetic classification even when the mailbox transport is real. The approved send's immutable recipient is the expected reply sender. Missing `simulated` options normalise to false, while both mock and real reply ingestion enforce consent. Signature validation, opaque reply tokens, sender matching and duplicate handling remain required.

An explicit `RESEND_TEST_RECIPIENT` configuration supports the documented `onboarding@resend.dev` test sender, only with `DEMO_MODE=true` and a matching single-address demo allowlist. This bypasses custom-domain lookup solely for that exact shared sender, never marks a domain verified, and checks the restricted recipient again before SDK sending. Normal senders still require verified sending-domain checks. Mock modes remain the code defaults. See `docs/integration-setup.md` for activation and account limits.

### Mock extraction and email-client formatting

Mock quote extraction accepts a known fixture identifier, or the explicit generic `[[MOCK_QUOTE_FIXTURE]]` marker only when the complete whitespace-normalised remaining body matches exactly one checked-in synthetic fixture. No prices, additional instructions or unfamiliar words may differ. Evidence is checked with the same whitespace normalisation, and the source email is never edited. This supports email-client line wrapping and copied generic demo markers without pretending to interpret arbitrary messages. Unsupported source messages can be explicitly retried through the same processing service after a supported format is added. OpenAI's separate demo transmission gate remains unchanged.
